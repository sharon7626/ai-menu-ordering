# AI 菜單點餐系統專案記憶

## 1. 文件用途與更新原則

本文件保存 `ai-menu-ordering` 專案已確認且需要跨工作階段延續的資訊，供開發代理與使用者在開始下一個小任務前快速掌握方向。

- 權威來源依序為：使用者目前明確指示、`AGENTS.md`、`doc/requirements.md`、本文件、`doc/todo.md`、相關規格文件與已驗證的實作結果。
- 只有在決策被確認、既有決策改變、重要限制被發現，或任務通過實際驗收時才更新。
- 不記錄猜測、未驗證成果、完整除錯過程或任何機密值。
- 更新目前進度時，只加入已完成且已測試的事實，不得預先宣告後續任務完成。

最後整理日期：2026-08-19。

## 2. 專案最終成果

1. 使用者上傳一張清楚的 JPG、PNG 或一頁式 PDF 菜單，由 AI 擷取分類、品項名稱與價格；團購主揪鎖定辨識內容並勾選本次提供品項，店家模式才提供菜單內容維護。
2. 一般使用者團購模式中，統籌建立團購代碼並分享給參與者。
3. 每位參與者輸入姓名、選擇餐點與數量，送單後取得個人訂單編號並查看自己的訂單。
4. 統籌使用獨立管理連結查看所有個人明細、餐點彙整及總金額，關閉團購後複製摘要向店家訂購。
5. 團購模式完成後增加店家固定菜單模式：店家預先設定菜單，顧客透過固定網址或 QR Code 點餐。
6. 統籌與店家從後台依姓名查看餐點，明確辨識每份餐點屬於誰；訂單編號仍由系統保存，但不放在個人明細標題。
7. 兩種模式共用菜單、購物車、訂單與管理畫面核心，但菜單與訂單資料彼此正確歸屬，不使用全站唯一正式菜單。
8. 訪客持續擁有完整主要功能；Google 登入是選擇性的保存與找回能力，提供我的團購、我的訂單與跨裝置使用，不形成強制會員制。
9. 全站以共用 Design System 建立安靜、自然、具有 editorial 層次的品牌體驗；首頁互動較強，點餐與管理頁逐步收斂，手機與 reduced-motion 必須安全降級。

## 3. 已確認技術與安全決策

- 前端使用 HTML、CSS、JavaScript，不使用 React 或 Vite。
- 後端使用 Python 與 FastAPI。
- 本機資料庫使用 SQLite。
- 使用 Git 與 GitHub 進行版本管理。
- 最後部署至 Render。
- 本機維持 SQLite；Render 正式環境已確認使用 PostgreSQL，透過 `DATABASE_URL` 連線。第一次部署從空資料庫開始；後續版本必須沿用並先備份既有正式資料庫，不可誤連新空資料庫。
- AI API 只能由後端呼叫；API Key 不得出現在 HTML、前端 JavaScript、瀏覽器畫面或前端打包檔案。
- API Key、密碼、Token、Cookie、Session Secret 與正式資料庫連線字串不得寫入程式碼或提交至 Git，必須透過環境變數讀取。
- Render 機密資料必須放在 Render Environment Variables，不得寫入 Repository。
- `.env.example` 只能包含變數名稱與安全示範值；不得建立或提交真正的 `.env`。
- 菜單上傳使用 `python-multipart` 接收瀏覽器檔案，並使用 `pypdf` 檢查 PDF 是否剛好一頁；兩者皆只由後端使用。
- 第一版單一菜單檔案大小上限已確認為 10 MB。
- 為避免專案產生額外 API 費用，AI 菜單辨識改用 Google Gemini Developer API 免費層，預設模型為 `gemini-3.6-flash`；免費額度有使用限制，模型與條款仍須在部署前再次確認。
- JPG、JPEG、PNG 與一頁式 PDF 以原始 bytes 和正確 MIME type 傳給 Gemini，不使用永久檔案上傳。
- AI 回應必須使用 JSON Schema 結構化輸出，契約位於 `doc/menu-recognition.schema.json`；看不清楚的名稱或價格使用 `null` 並交由店家修正，不得猜測。
- Gemini 免費層提交的內容可能用於改善 Google 產品，因此現階段只處理公開且不含機密資訊的餐廳菜單。
- 選擇性登入已確認使用 Firebase Authentication 的 Google Sign-In；前端取得 Firebase ID Token，FastAPI 必須在後端驗證後才可使用可信任 UID。
- Google 登入不取代既有 management Token 與 order view Token。訪客資料的 Claim 必須同時驗證登入身分與原始私密 Token，只知道團購碼、姓名或訂單編號不得 Claim。
- 使用者資料採最小原則，不保存 Google Access Token；`group_sessions.owner_user_id` 與 `orders.user_id` 必須允許 `NULL`，讓既有及未登入訪客資料持續有效。

## 4. 菜單資料決策

- 所有人工建立或 AI 辨識的菜單，都必須轉換為 `doc/menu-data-spec.md` 定義的統一 JSON 格式。
- `data/menu.json` 保留為開發與未串接 AI 時的示範菜單，不再視為團購模式與店家模式共同覆寫的正式資料位置。
- 點餐頁面只讀取統一菜單資料，不因不同菜單圖片或版面重新製作網站。
- 分類與餐點必須依當次確認後的菜單資料動態產生，不得寫死為飯類、麵類或任何固定分類；目前的飯類與麵類只供第一階段測試。
- 菜單包含餐廳名稱、分類，以及餐點的識別碼、名稱、說明、非負整數價格與供應狀態。
- 團購菜單屬於單一團購並保存為快照；店家固定菜單屬於店家。菜單歸屬、團購狀態與管理 Token 由資料庫保存，不放進菜單內容 JSON。
- 團購代碼是參與者公開入口；統籌管理連結使用不可猜測的私密 Token；個人訂單編號用來辨識每位參與者或顧客的餐點，三者不可混用。
- 訂單必須保存送單當下的品項名稱與單價，避免菜單更新改變歷史訂單。
- 第一版資料格式不支援糖度、冰量、加料、尺寸、套餐或其他複雜客製選項。

## 5. 開發順序

### 第一階段：點餐底座

固定 `menu.json` → 菜單顯示 → 購物車 → 訂單表單 → FastAPI → SQLite → 管理後台。

第一階段必須在未串接 AI 時仍可獨立使用。

### 第二階段：AI 菜單匯入（已完成至人工確認）

菜單檔案上傳 → AI 辨識 → 團購勾選供應品項／店家維護菜單。

### 第三階段：一般使用者團購模式（優先）

團購資料格式 → 團購資料表 → 建立團購代碼與管理連結 → 參與者送單與個人訂單 → 統籌個人明細與餐點彙整 → 關閉團購與複製摘要 → 整合驗收。

### 第四階段：店家固定菜單模式

店家固定菜單 → 固定網址與 QR Code → 顧客個人訂單 → 店家訂單後台 → 雙模式整合驗收。

### 第五階段：發布前操作體驗補強

雙模式首頁 → 每個餐點的自由文字備註 → 全站返回與首頁導覽 → 店家固定菜單分類與品項增刪。

### 第六階段：發布準備

測試 → GitHub → Render 與正式部署。

### 第七階段：選擇性登入與品牌體驗升級

Firebase Token 驗證 → 使用者資料與選填關聯 → 登入建立／送單綁定 → 我的團購 → 我的訂單 → 安全 Claim → 我的菜單可行性評估 → 共用 Design System → 首頁與內頁品牌改版 → 完整安全、功能、UI、效能與無障礙驗收 → 新版部署前清單。
