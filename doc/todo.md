# AI 菜單點餐系統開發待辦

## 使用方式

- 依序完成任務，每項完成後再進入下一項。
- 每個任務需通過列出的驗收方式才可勾選。
- 第一階段須保持不依賴 AI 功能也能獨立運作。
- 未勾選任務不得提前實作；產品方向改變時，先更新需求與任務順序再繼續開發。

## 第一階段：點餐底座

- [x] **1. 建立 `menu.json` 資料格式與範例資料（Done）**
  - 定義分類、品項識別碼、品項名稱與價格欄位。
  - 建立至少兩個分類及每類至少兩個品項的範例。
  - 驗收：檔案為合法 JSON；所有品項具備唯一識別碼、名稱與非負整數價格；格式能表達分類與其品項。
  - 對應：FR-01、AC-01。

- [x] **2. 建立靜態點餐頁面骨架（Done）**
  - 建立基本 HTML 結構及必要的 CSS、JavaScript 檔案入口，不使用 React 或 Vite。
  - 驗收：瀏覽器可直接開啟頁面，頁面具備菜單區與購物車區的明確容器，且無載入錯誤。
  - 對應：FR-02。

- [x] **3. 讀取並顯示 `menu.json`（Done）**
  - 依分類渲染品項名稱與價格。
  - 驗收：範例資料中的所有分類及品項皆正確顯示，價格顯示一致。

- [x] **4. 實作品項數量調整（Done）**

## 第二階段：AI 菜單匯入

  - 驗收：允許的格式可進入處理流程，不允許的格式會收到明確錯誤訊息。
  - 對應：FR-09。

- [x] **15. 建立菜單檔案上傳介面與 API（Done）**
  - 提供單一菜單檔案的選擇、上傳與基本驗證。
  - 驗收：三種允許格式皆可成功上傳；多頁 PDF 與不允許格式會被拒絕。
  - 對應：FR-09。

- [x] **16. 確認 AI API 方案與結構化輸出契約（Done）**
  - 選定供應商與模型，定義分類、品項名稱與價格的輸出結構及錯誤處理方式。
  - 驗收：決策與資料契約完成文件化，且輸出可轉換為第一階段的 `menu.json` 格式。
  - 對應：FR-10。

- [x] **17. 串接 AI 菜單辨識流程（Done）**

  - 驗收：以清楚的測試菜單可取得分類、品項名稱及價格；失敗時不寫入正式菜單並顯示可理解的錯誤。
  - 對應：FR-10。

- [x] **18. 建立辨識結果確認與修改介面（Done）**
  - 店家可修改分類、品項名稱及價格，再進行確認。
  - 驗收：修改後畫面與送出資料一致；無效或缺漏資料不可確認。
  - 對應：FR-11。

- [x] **19. 確認雙模式產品方向與資料歸屬（Done）**
  - 將產品分成優先開發的團購模式，以及後續店家固定菜單模式；兩者共用菜單、購物車與訂單核心。
  - 驗收：需求文件清楚區分團購代碼、統籌管理連結、個人訂單編號、團購菜單快照與店家固定菜單，且不再將 `data/menu.json` 視為全站正式菜單。
  - 對應：FR-14 至 FR-26。
