# AI 菜單點餐系統需求規格

最後更新：2026-08-19

## 1. 文件目的

本文件記錄已確認的產品方向、功能需求、開發階段、驗收條件與範圍限制。系統採用共用的菜單與點餐核心，依使用情境分成「一般使用者團購模式」與「店家固定菜單模式」。

## 2. 專案目標

系統讓使用者上傳一張清楚的 JPG、PNG 或一頁式 PDF 菜單，由 AI 擷取分類、品項名稱與價格，人工確認後建立可點餐的菜單。

第一個主要情境是一般使用者的團體點餐：統籌建立團購、分享團購代碼，參與者各自點餐，最後由統籌取得個人明細與餐點統計，再自行打電話或傳訊息向店家訂購。

第二個情境是店家固定菜單：店家預先設定長期菜單，顧客透過固定網址或 QR Code 點餐，店家可依個人訂單編號與姓名查看每位顧客的餐點。

## 3. 名詞與使用角色

### 3.1 重要名詞

| 名詞 | 用途 |
| --- | --- |
| 團購代碼 | 統籌分享給參與者的短代碼，用來進入同一次團購。 |
| 統籌管理連結 | 只有統籌持有的不可猜測連結，用來查看全部訂單、統計與關閉團購；不得當作一般分享連結。 |
| 個人訂單編號 | 每位參與者或顧客送單後取得的編號，用來辨識自己的餐點。 |
| 團購菜單快照 | 某次團購確認後的菜單副本；後續其他菜單變更不得影響已建立的團購。 |
| 店家固定菜單 | 某一店家預先設定並長期使用的菜單，不是全站唯一共用檔案。 |

### 3.2 使用角色

| 角色 | 主要行為 |
| --- | --- |
| 統籌 | 上傳與確認菜單、建立團購、分享代碼、查看個人明細與彙整結果、關閉團購。 |
| 團購參與者 | 使用團購代碼進入菜單、輸入姓名、點餐；訪客另提供手機或 Email，登入者沿用已驗證的 Google 帳號身分；送單後取得個人訂單編號並查看自己的訂單。 |
| 店家 | 預先設定固定菜單、提供固定網址或 QR Code、查看顧客訂單。 |
| 店家顧客 | 掃描 QR Code 或開啟固定網址、輸入姓名並點餐；訪客另提供手機或 Email，登入者沿用已驗證的 Google 帳號身分；送單後取得個人訂單編號。 |

系統不採強制會員制。訪客仍可上傳菜單、建立或加入團購、點餐、分享、使用既有管理連結與個人訂單連結，以及使用店家固定菜單。使用者可選擇以 Google 登入，取得「我的團購」、「我的訂單」及跨裝置找回能力。店家模式目前仍只支援單一店家情境，不建立多店家帳戶平台。

## 4. 功能需求

### 4.1 已完成的共用點餐底座

| 編號 | 需求 |
| --- | --- |
| FR-01 | 系統應能從統一菜單資料讀取分類、品項名稱、說明、價格與供應狀態。 |
| FR-02 | 點餐頁面應依菜單資料動態顯示分類與品項，不得寫死為飯類或麵類。 |
| FR-03 | 使用者應可加入多個品項並調整各品項數量。 |
| FR-04 | 購物車應顯示已選品項、數量、小計與總金額。 |
| FR-05 | 使用者應輸入姓名後才能送出訂單。 |
| FR-06 | 系統應將有效訂單與明細完整儲存至資料庫。 |
| FR-07 | 管理畫面應能查看訂單編號、姓名、品項、數量與總金額。 |
| FR-08 | 未串接 AI 時，固定示範菜單的點餐底座仍應可獨立使用。 |

### 4.2 已完成的 AI 菜單匯入

| 編號 | 需求 |
| --- | --- |
| FR-09 | 系統應接受 JPG、PNG 或一頁式 PDF 菜單，單一檔案上限為 10 MB。選擇檔案後應先顯示預覽；JPG、PNG 可在送交辨識前框選菜單範圍，一頁式 PDF 先提供整頁預覽。 |
| FR-10 | AI 應擷取原菜單的餐廳名稱、分類、品項名稱及價格，不得固定分類或猜測模糊內容；同品項有 L／XL、大小份等明確多種價格時，應拆成名稱含規格且價格正確的獨立可點項目，不得只因多價格而全部留空。 |
| FR-11 | 店家模式可確認及修改辨識結果；團購模式鎖定 AI 擷取的分類、品項與價格，主揪只勾選本次要提供的品項，並可依品項名稱、分類與最高價格篩選。若 AI 未辨識到餐廳名稱，兩種模式都必須允許使用者手動輸入名稱；已辨識到名稱時團購模式維持鎖定。使用篩選時，符合結果的品項就是建立團購後實際提供的品項；同品項的括號規格應合併顯示但仍可分別勾選。若團購菜名或價格辨識有誤，應改用較清楚的圖片重新辨識，不在確認頁改價。 |
| FR-12 | 無效或缺漏的辨識資料不得確認；AI 失敗或辨識不完整時不得覆寫正式資料。 |
| FR-13 | AI API Key 只能由後端透過環境變數使用。 |

### 4.3 一般使用者團購模式（優先開發）

| 編號 | 需求 |
| --- | --- |
| FR-14 | 統籌確認菜單後，系統應建立一個獨立團購及其菜單快照。 |
| FR-15 | 系統應為團購產生可分享的團購代碼，以及只有統籌持有的管理連結。 |
| FR-16 | 參與者應可用團購代碼或分享連結進入正確菜單，輸入姓名並點餐。 |
| FR-17 | 每次有效送單應取得個人訂單編號，參與者應可查看自己的姓名、餐點、數量與金額。 |
| FR-18 | 統籌應可查看該團購所有參與者的個人訂單，但一般參與者不可進入統籌管理畫面；管理頁的個人明細以參與者姓名為標題，不附加訂單代碼。 |
| FR-19 | 系統應同時提供「依參與者」與「依餐點及備註需求」兩種彙整，包含品項總數量與金額；相同品項但備註不同時必須分列，並在畫面與輸出中相鄰排列於同一品項之下。 |
| FR-20 | 統籌應可關閉團購；關閉後不得再接受新訂單。 |
| FR-21 | 統籌應可複製適合貼到通訊軟體的純文字訂單摘要，並在至少已有一張訂單時下載含「餐點彙整」、「訂購者合計」與「個人明細」工作表的 Excel 檔。「訂購者合計」每張送出的訂單各列一筆姓名、餐點總數量、合計金額與送單時間；同名的不同訂單不得合併。Excel 必須包含實際姓名、品項、備註、單價、數量、小計與團購總額，且不得包含管理 Token。 |

### 4.4 店家固定菜單模式（團購模式完成後開發）

| 編號 | 需求 |
| --- | --- |
| FR-22 | 店家應可預先設定並更新自己的固定菜單；不得使用全站共用的唯一菜單檔案表示所有情境。 |
| FR-23 | 系統應提供店家固定點餐網址，並可產生供顧客掃描的 QR Code。 |
| FR-24 | 顧客進入店家網址後，只能看到該店家設定的菜單，並可用與團購模式相同的購物車與姓名流程點餐。 |
| FR-25 | 每張店家訂單應取得個人訂單編號，顧客可查看自己的訂單。 |
| FR-26 | 店家後台應同時提供「依品項及備註需求彙整」與「個別顧客訂單」，讓店家能辨識每份餐點屬於誰並掌握各品項總數量與金額；店家可在至少已有一張訂單時下載含「餐點彙整」、「顧客合計」與「顧客明細」的 Excel，且檔案不得包含管理 Token。 |

### 4.5 發布前操作體驗補強

| 編號 | 需求 |
| --- | --- |
| FR-27 | 系統首頁應清楚提供「主揪建立團購」、「參與者使用代碼加入」與「店家固定菜單」三個主要入口；只有主揪或店家需要上傳菜單，團購參與者直接輸入主揪分享的代碼點餐。早期固定示範菜單不得出現在正常使用流程。 |
| FR-28 | 每個主要操作分頁都應在頁面最上方提供單一、清楚的「首頁」按鈕；頁面內需要時可另提供符合流程的返回操作，但不得把管理 Token 放進公開網址或 QR Code。 |
| FR-29 | 店家建立或更新固定菜單時，除了修改 AI 辨識內容，也應能新增或刪除分類及品項。此能力不提供給團購模式；同一品項的括號規格應在確認畫面合併成同一列呈現，但保存時仍保留各規格的名稱與價格。 |
| FR-30 | 團購參與者及店家顧客可為每個已選餐點填寫最多 200 字的選填自由文字備註，例如「小辣」或「半糖少冰」；備註不改變菜單單價，第一版不建立固定規格選單或自動加價。 |
| FR-31 | 團購及店家點餐頁應使用緊湊清單呈現品項、價格與數量；不限 L／XL，同一 base item 的括號規格應顯示在同一列，每個規格仍保留獨立 item id、價格、供應狀態、數量與備註；餐點尚未選取時隱藏其備註欄，選取後只展開該品項備註。 |

### 4.6 選擇性 Google 登入與跨裝置找回

| 編號 | 需求 |
| --- | --- |
| FR-32 | Google 登入必須是選擇性功能；未登入訪客仍可完整使用既有團購、訂單、管理連結、店家固定菜單、Excel 與 QR Code 流程。 |
| FR-33 | 前端使用 Firebase Authentication 的 Google Sign-In 取得 Firebase ID Token；FastAPI 必須在後端驗證 Token，並只使用驗證後的 Firebase UID 作為可信任身分，不得相信前端自行傳入的 `user_id`、email 或 display name 進行授權。 |
| FR-34 | 系統應保存最小使用者資料：Firebase UID、email、顯示名稱及建立／更新時間；不得保存 Google Access Token。 |
| FR-35 | 登入使用者建立團購時，系統應把團購綁定至該使用者；未登入建立的團購維持訪客資料且 `owner_user_id` 為 `NULL`。 |
| FR-36 | 登入使用者送出團購或店家訂單時，系統應把訂單綁定至該使用者；未登入送單仍維持既有流程且 `user_id` 為 `NULL`。 |
| FR-37 | 登入後的「我的團購」只顯示目前使用者擁有的團購，並可跨裝置進入該團購的管理資料；不得因只知道公開團購碼而取得管理權限。既有 management Token 管理方式必須保留。 |
| FR-38 | 登入後的「我的訂單」只顯示目前使用者所屬的訂單，並可跨裝置查看；不得顯示其他使用者或訪客的私人訂單。既有 order view Token 查看方式必須保留。 |
| FR-39 | 訪客建立團購後登入，只有同時持有有效 management Token 才能將該團購綁定至自己的帳號；只知道團購碼不得 Claim。 |
| FR-40 | 訪客送單後登入，只有同時持有有效 order view Token 才能將該訂單綁定至自己的帳號；姓名、團購碼或訂單編號不得單獨作為 Claim 依據。 |
| FR-41 | 系統只支援 Google 登入、登出與登入狀態維持；本階段不加入 Email＋密碼、忘記密碼、SMS、LINE、Facebook、Apple 登入、會員等級或大頭照上傳。 |
| FR-49 | 登入者可將本人「我的團購」與「我的訂單」封存、查看已封存項目並恢復；封存只整理帳號清單，不得刪除或改變團購、訂單、管理頁、公開頁及 Excel 資料。再次開團應沿用「我的菜單」建立新團購，不重複建立另一套菜單複製邏輯。 |
| FR-50 | 「我的訂單」應將本人經營的店家固定菜單與本人送出的訂單分區顯示；店家區提供調整菜單、店家收到的訂單及顧客點餐頁入口。舊店家只有持有原 management Token 才能綁定，不能因曾在該店送單就取得店家權限。 |
| FR-51 | 「我的菜單」應同時顯示團購常用菜單與本人店家固定菜單；固定菜單須明確標示並提供調整、店家訂單及公開點餐頁入口。舊固定菜單可由登入者貼入含正確 management Token 的原完整管理連結安全認領。 |
| FR-52 | 店家固定菜單的建立完成頁、店家訂單後台及「我的菜單」應共用同一調整入口；進入後先載入目前菜單供直接增刪修改，也可選擇上傳全新菜單重新辨識。兩種方式都必須沿用既有管理 Token 或帳號擁有者權限，且不得改變固定公開網址、QR Code 或歷史訂單快照。 |
| FR-53 | 團購與店家送單必須有可追溯身分：登入者以後端驗證的 Google 帳號為準，不重複要求聯絡資料；未登入訪客必須擇一提供臺灣手機號碼或 Email。聯絡資料只可顯示於具管理權限的訂單後台與 Excel，不得出現在公開菜單、分享頁或 QR Code。既有未記錄身分的歷史訂單仍須可讀。此機制不包含簡訊或 Email 驗證碼，因此只增加可追溯性與嚇阻，不能保證聯絡方式確由填寫者持有。 |
| FR-54 | 團購與店家固定菜單送單 API 必須共同具備基本防濫用保護：30 秒內相同來源、身分與內容的訂單不得重複建立；同一來源及身分對同一菜單 10 分鐘最多完成 5 次建立或更新送單；前後端加入正常使用者看不到的機器人誘捕欄位，欄位被填寫時拒絕送單。保護紀錄只可在記憶體保存不可逆雜湊，不得保存或記錄原始 IP、手機、Email、Token 或訂單個資。 |
| FR-55 | 同一個 Google 帳號或同一個正規化訪客聯絡方式，在同一個團購中只保留一張目前訂單。再次送單時，原裝置或已驗證帳號必須先選擇「加購」或「修改原訂單」；加購保留原內容並加入本次內容，修改則以本次內容取代，兩者都沿用原訂單編號。僅知道手機或 Email 不足以在另一台裝置修改訪客訂單，必須持有第一次送單留下的私密憑證。店家固定菜單屬持續營業情境，不套用永久單一訂單限制。 |

## 5. 菜單與訂單資料原則

1. `data/menu.json` 保留為開發與未串接 AI 時的示範資料，不再視為未來所有使用者共用的正式菜單。
2. 團購菜單屬於特定團購，建立後形成快照。
3. 店家固定菜單屬於特定店家；第一版店家模式只做單一店家，但資料不可設計成無法擴充。
4. 訂單必須記錄送單當下的品項名稱、單價、數量與該餐點備註，避免菜單後續修改造成舊訂單改變。
5. 團購代碼、統籌管理連結與個人訂單編號用途不同，不可共用同一個公開值。
6. 參與者只需看到自己的訂單；統籌管理連結才可查看團購全部明細。
7. 使用者帳號關聯是選填欄位；`NULL` 代表訪客，既有訪客資料與 Token 連結持續有效。
8. Google 登入提供保存與找回能力，不得取代既有的公開代碼、management Token 或 order view Token 安全邊界。

更完整的模式差異與流程位於 `doc/ordering-modes-spec.md`。

## 6. 展示流程

### 6.1 團購模式

1. 統籌上傳菜單圖片或一頁式 PDF。
2. AI 擷取分類、品項名稱與價格。
3. 統籌確認並修正辨識結果。
4. 系統建立團購代碼與統籌管理連結。
5. 參與者使用代碼進入菜單並點餐；登入者沿用 Google 帳號身分，訪客輸入姓名並擇一提供手機或 Email。
6. 系統為每位身分建立一個個人訂單編號；同一身分再次送單時可加購或修改，並沿用原編號。
7. 統籌查看個人明細及依餐點彙整結果。
8. 統籌關閉團購並複製訂單摘要。
9. 統籌自行打電話或傳訊息向店家訂購。

### 6.2 店家模式

1. 店家預先建立並確認固定菜單。
2. 系統提供固定網址與 QR Code。
3. 顧客進入後只看到該店菜單。
4. 顧客選擇餐點及數量；登入者沿用 Google 帳號身分，訪客輸入姓名並擇一提供手機或 Email 後送單。
5. 顧客取得個人訂單編號並查看自己的餐點。
6. 店家從後台查看依品項統整及個別顧客訂單，並可下載 Excel 訂單表。

## 8. 技術與平台限制

- 前端使用 HTML、CSS、JavaScript，不使用 React 或 Vite。
- 後端使用 Python 與 FastAPI。
- 本機資料庫使用 SQLite。
- AI 使用 Google Gemini Developer API 免費層，預設模型為 `gemini-3.6-flash`。
- 使用 Git 與 GitHub 進行版本管理。
- 最後預定部署至 Render。
- Render 正式環境使用 PostgreSQL，透過 `DATABASE_URL` 連線；本機仍使用 SQLite。
- API Key 只能放在後端環境變數，不得進入前端或 Repository。
- 選擇性登入使用 Firebase Authentication 與 Google Sign-In；FastAPI 使用 Firebase Admin SDK 驗證 ID Token。
- Firebase Admin credential、正式 Firebase 設定與其他機密只能透過環境變數或 Render Secret 設定，不得提交至 Git。

## 9. 本階段不包含

- 強制登入；訪客仍保留完整主要功能。
- Email＋密碼、忘記密碼、SMS、LINE、Facebook 或 Apple 登入。
- 會員等級、付費會員、完整會員中心或大頭照上傳。
- 多店家帳戶與多分店管理平台。
- 外送員與派單。
- 線上付款。
- 電子發票。
- 自動傳送 LINE、Messenger 或簡訊。
- POS 串接。
- 複雜套餐。
- 固定的加料、大小杯、冰量、糖量選單與自動加價；第一版只提供不影響價格的自由文字餐點備註。
- 保證辨識所有手寫或複雜菜單。
- 店家廚房出單設備或標籤列印整合。

## 10. 部署階段決策與待確認事項

- Render 免費或付費方案是否符合預期流量。
- 正式環境已確認使用 Render PostgreSQL；第一次部署從空資料庫開始且不搬本機測試資料，後續新版沿用既有正式資料庫並在備份後執行 additive migration。
- Gemini 免費層的模型、額度與資料使用條款是否仍符合需求。
- Firebase Console 的專案、Google provider、Authorized Domains 與 Web App 設定，需在程式與 migration 全部測試完成後由使用者逐步設定。
- 新版正式部署前必須先完成 PostgreSQL migration 備份與驗證，並向使用者說明 GitHub push 後 Render 的行為；未經批准不得部署。
