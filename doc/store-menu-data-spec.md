# 店家固定菜單資料格式與入口規格

## 1. 文件目的

本文件定義第一版店家固定菜單模式的資料歸屬、公開入口、私密管理入口與安全規則。店家先建立一份長期使用的菜單，顧客透過固定網址或 QR Code 點餐；店家更新菜單後，網址維持不變。

第一版操作介面只提供單一店家情境，不建立會員登入或多店家帳戶平台；資料仍以店家識別碼建立關聯，避免日後只能使用全站唯一菜單。

本文件是 Todo 第 31 項之後建立資料表與功能的依據；店家資料、固定公開頁與 QR Code 已依本規格完成，後續接續顧客訂單與店家管理功能。

## 2. 與團購模式的差異

| 項目 | 團購模式 | 店家固定菜單模式 |
| --- | --- | --- |
| 菜單生命週期 | 每次團購建立一份不可變快照 | 店家可更新目前菜單 |
| 公開入口 | 單次團購代碼 | 長期固定店家網址 |
| 管理者 | 團購統籌 | 店家 |
| 管理入口 | 單次團購私密連結 | 店家私密管理連結 |
| 訂單接收 | 統籌彙整後自行聯絡店家 | 店家直接從後台查看 |
| 暫停接單 | 關閉單次團購 | 本規格暫以店家 `active` 狀態控制 |

兩種模式共用統一菜單格式、購物車、後端重新核價、個人訂單編號及 Token 安全原則，但資料不可互相混入。

## 3. 店家資料 `store_profiles`

| 欄位 | 建議型別 | 必填 | 用途與規則 |
| --- | --- | --- | --- |
| `id` | INTEGER | 是 | 資料庫內部主鍵，不公開且不可作為權限憑證。 |
| `public_slug` | TEXT | 是 | 店家固定公開識別碼，全系統不可重複；建立後第一版不修改。 |
| `management_token_hash` | TEXT | 是 | 店家管理 Token 的 SHA-256 雜湊；資料庫不得保存原始 Token。 |
| `active` | INTEGER | 是 | `1` 表示接受新訂單，`0` 表示暫停接單。 |
| `next_order_sequence` | INTEGER | 是 | 下一張店家訂單流水號，初始為 `1`。 |
| `created_at` | TEXT | 是 | UTC ISO 8601 建立時間。 |
| `updated_at` | TEXT | 是 | UTC ISO 8601 最後更新時間。 |

### 公開識別碼規則

- 使用 8 碼小寫英文字母，例如 `abcdefgh`。
- 格式：`^[a-z]{8}$`。
- 使用 Python `secrets` 模組產生，並由資料庫 `UNIQUE` 限制避免重複。
- 識別碼可以公開，用來組成固定網址，但不代表店家管理權限。
- 第一版由系統產生，不增加店家自訂網址名稱功能。

## 4. 店家目前菜單 `store_menus`

| 欄位 | 建議型別 | 必填 | 用途與規則 |
| --- | --- | --- | --- |
| `store_profile_id` | INTEGER | 是 | 對應一個店家；每個店家只有一份目前生效菜單。 |
| `menu_json` | TEXT | 是 | 符合 `doc/menu-data-spec.md` 的完整 UTF-8 JSON。 |
| `version` | INTEGER | 是 | 菜單版本，初始為 `1`，每次成功更新加 `1`。 |
| `created_at` | TEXT | 是 | 第一次建立時間。 |
| `updated_at` | TEXT | 是 | 最後成功更新時間。 |

更新規則：

- 更新前必須通過與建立菜單相同的人工確認與格式驗證。
- 更新只替換該店家目前公開菜單，不改變 `public_slug`、公開網址或 QR Code。
- 更新不得修改其他店家、團購菜單快照或 `data/menu.json`。
- 舊訂單繼續使用 `order_items` 保存的送單當下名稱、單價與餐點備註，不因菜單更新而改變。
- 顧客可為每個已選餐點填寫最多 200 字的自由文字備註；備註不改變目前菜單單價。
- 第一版不建立完整歷史菜單版本表；`version` 用於辨識目前菜單已更新幾次。

## 5. 店家顧客訂單關聯

後續需在現有 `orders` 加入：

| 欄位 | 建議型別 | 店家訂單必填 | 用途與規則 |
| --- | --- | --- | --- |
| `store_profile_id` | INTEGER / NULL | 是 | 所屬店家。非店家訂單保持 `null`。 |
| `public_order_number` | TEXT / NULL | 是 | 顧客個人訂單編號，例如 `S-ABCDEF-001`；沿用現有唯一欄位。 |
| `order_access_token_hash` | TEXT / NULL | 是 | 顧客個人查看 Token 雜湊；沿用現有欄位。 |

店家訂單只能屬於一個店家，且 `group_session_id` 必須為 `null`；團購訂單的 `store_profile_id` 必須為 `null`。第一階段示範訂單可同時不屬於團購或店家。

個人訂單編號使用完整店家公開識別碼的大寫形式，例如店家 `abcdefgh` 的第一張訂單為 `S-ABCDEFGH-001`。後端必須在單一資料庫交易中取得並遞增流水號，避免多人同時送單時重複，也避免不同店家前 6 碼相同時發生編號衝突。

## 6. 公開入口與 QR Code

### 固定公開網址

格式：

```text
/stores/{public_slug}
```

例如：

```text
/stores/abcdefgh
```

公開網址只用來：

- 讀取該店家目前菜單與接單狀態。
- 讓顧客選餐、輸入姓名及送單。
- 絕對不可回傳店家管理 Token、管理 Token 雜湊或其他店家的資料。

### QR Code

- QR Code 內容只能是完整的固定公開網址。
- 不得包含 `#token=`、查詢參數形式的 Token、Cookie、資料庫 ID 或店家管理資訊。
- 菜單更新後 QR Code 不需重新產生，因為固定網址不變。
- QR Code 由後端使用 `qrcode 8.2` 產生 SVG 圖檔，不依賴外部 QR Code 服務；內容只包含依目前網站來源組成的完整公開網址。

## 7. 店家管理入口

格式：

```text
/stores/{public_slug}/manage#token=<store-management-token>
```

安全規則：

- 原始 Token 使用 `secrets.token_urlsafe(32)` 產生，只在建立店家成功時回傳一次。
- 資料庫只保存 SHA-256 雜湊，使用 `hmac.compare_digest` 驗證。
- Token 放在網址片段 `#token=`，不會隨頁面網址傳送到伺服器；前端再以 `Authorization` 標頭送給受保護 API。
- 公開網址與 QR Code 不得包含管理 Token。
- 管理 Token 可更新菜單、查看店家訂單及切換接單狀態；顧客個人 Token 不具店家管理權限。
- 第一版沒有會員登入，因此管理連結遺失時無法自行取回原始 Token；後續若需要復原機制，必須先另訂安全規格。

## 8. 店家菜單建立與更新流程

1. 店家上傳 JPG、PNG 或一頁式 PDF。
2. AI 辨識分類、品項名稱與價格。
3. 店家人工修正並確認。
4. 第一次確認時建立 `store_profiles`、`store_menus`、固定公開網址與私密管理連結。
5. 之後店家從私密管理入口上傳並確認新菜單，只更新自己的 `store_menus`。
6. 顧客開啟原固定網址時，自動看到更新後菜單。
7. 所有舊訂單仍顯示送單當時的名稱、單價、數量與小計。

## 9. 權限表

| 持有資料 | 可以做的事 | 不可以做的事 |
| --- | --- | --- |
| 店家公開網址或 QR Code | 查看目前菜單、在接單中送出自己的訂單 | 更新菜單、查看所有顧客、取得管理 Token |
| 顧客個人訂單編號與 Token | 查看該張個人訂單 | 查看其他顧客或店家後台 |
| 店家管理 Token | 更新菜單、查看店家全部訂單、切換接單狀態 | 取得資料庫中的原始 Token（資料庫沒有保存） |
| 資料庫內部 ID | 僅供關聯 | 不可單獨通過公開或管理權限驗證 |

## 10. 第一版暫時不處理

- 多店家帳號註冊、登入、密碼重設與權限角色。
- 多分店、分店限定菜單或跨店訂單。
- 店家自訂網址文字。
- 菜單完整版本歷史與還原。
- 線上付款、出餐狀態、外送、通知、POS 或列印設備。
- 管理 Token 遺失後的自助復原。

## 11. 需求追溯

- `FR-22`：店家固定菜單屬於店家，可更新且不使用全站唯一正式菜單。
- `FR-23`：提供不含管理資訊的固定網址與 QR Code。
- `FR-24`：顧客只看到該店家目前菜單並使用共用點餐流程。
- `FR-25`：店家顧客訂單有獨立編號與私密個人查看方式。
- `FR-26`：店家管理入口可依訂單編號與姓名查看餐點。
