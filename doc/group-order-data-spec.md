# 團購資料格式與安全規格

## 1. 文件目的

本文件定義一般使用者團購模式所需的資料格式與安全規則。目標是讓一個團購可以保存自己的菜單快照、讓多位參與者分別送出訂單，並讓統籌安全地查看彙整結果。

本文件是後續建立 SQLite 資料表與 FastAPI 功能的依據；目前只定義規格，不建立資料表、API 或頁面。

## 2. 核心資料關係

一個團購包含：

- 一筆團購資料 `group_sessions`。
- 一份建立團購當下的菜單快照 `group_menus`。
- 零至多筆參與者訂單 `orders`。
- 每筆訂單包含一至多筆餐點明細 `order_items`。

菜單快照建立後不隨 `data/menu.json` 或其他菜單變動。這能確保參與者看到的名稱與價格，和統籌最後彙整的內容一致。

## 3. 團購資料 `group_sessions`

| 欄位 | 建議型別 | 必填 | 用途與規則 |
| --- | --- | --- | --- |
| `id` | INTEGER | 是 | 資料庫內部主鍵，不公開，也不能當作權限憑證。 |
| `public_code` | TEXT | 是 | 6 碼公開團購代碼，全系統不可重複。 |
| `management_token_hash` | TEXT | 是 | 統籌管理 Token 經 SHA-256 雜湊後的 64 碼小寫十六進位文字。資料庫不得保存原始 Token。 |
| `status` | TEXT | 是 | 只允許 `open` 或 `closed`。 |
| `next_order_sequence` | INTEGER | 是 | 下一張個人訂單的流水號，初始為 `1`，必須大於或等於 `1`。 |
| `created_at` | TEXT | 是 | 建立時間，使用 UTC 的 ISO 8601 格式。 |
| `closed_at` | TEXT / NULL | 否 | 關閉時間。開放時必須是 `null`，關閉時必須有值。 |

### 團購代碼規則

- 使用字元：`ABCDEFGHJKLMNPQRSTUVWXYZ23456789`。
- 不使用容易混淆的 `I`、`O`、`0`、`1`。
- 格式：`^[A-HJ-NP-Z2-9]{6}$`。
- 範例：`ABC234`。
- 必須用 Python `secrets` 模組隨機產生，並以資料庫唯一限制避免重複；若碰撞就重新產生。
- 團購代碼可以分享給參與者，但它只是尋找團購的公開識別碼，不代表管理權限。

### 團購狀態規則

| 狀態 | 可查看菜單 | 可新增訂單 | 統籌可查看彙整 |
| --- | --- | --- | --- |
| `open` | 是 | 是 | 是 |
| `closed` | 是 | 否 | 是 |

第一版不提供重新開啟或刪除團購。關閉團購時，必須在同一個資料庫交易中將 `status` 改為 `closed` 並寫入 `closed_at`。

## 4. 菜單快照 `group_menus`

| 欄位 | 建議型別 | 必填 | 用途與規則 |
| --- | --- | --- | --- |
| `group_session_id` | INTEGER | 是 | 對應一個團購；每個團購只能有一份菜單快照。 |
| `menu_json` | TEXT | 是 | 完整菜單 JSON，必須符合 `doc/menu-data-spec.md`。 |
| `created_at` | TEXT | 是 | 快照建立時間，使用 UTC 的 ISO 8601 格式。 |

菜單快照必須符合下列規則：

- 必須是有效的 UTF-8 JSON。
- 必須包含餐廳名稱、至少一個分類及至少一個餐點。
- 分類與餐點的識別碼、名稱、價格及供應狀態，必須符合菜單資料規格。
- 建立團購前鎖定 AI 辨識的名稱與價格，主揪只選擇本次提供的餐點。若辨識有誤，應使用較清楚的圖片重新辨識；建立團購後不修改快照。
- 每張訂單只能選擇這份快照內 `available` 為 `true` 的餐點。

## 5. 個人訂單 `orders`

現有 `orders` 資料需在後續任務加入以下欄位，同時保留既有點餐底座資料的相容性：

| 欄位 | 建議型別 | 團購訂單必填 | 用途與規則 |
| --- | --- | --- | --- |
| `group_session_id` | INTEGER / NULL | 是 | 所屬團購。既有非團購示範訂單可保留為 `null`。 |
| `public_order_number` | TEXT / NULL | 是 | 給參與者辨識的個人訂單編號，例如 `ABC234-001`；全系統不可重複。既有訂單可為 `null`。 |
| `order_access_token_hash` | TEXT / NULL | 是 | 個人訂單查看 Token 的 SHA-256 雜湊。既有訂單可為 `null`。 |
| `customer_name` | TEXT | 是 | 參與者姓名，去除前後空白後須為 1 至 50 個字元。 |
| `total_amount` | INTEGER | 是 | 訂單總金額，必須是大於或等於 0 的整數，且由後端重新計算。 |
| `created_at` | TEXT | 是 | 送單時間，使用 UTC 的 ISO 8601 格式。 |

個人訂單編號由團購代碼加三位以上流水號組成。後端必須在同一個資料庫交易中讀取並遞增 `next_order_sequence`，再建立訂單，避免多人同時送單時取得相同編號。流水號超過 999 時可以自然增加位數。

個人訂單編號是方便人閱讀的識別碼，不是查看權限。參與者要查看自己的訂單時，仍須提供建立訂單時取得的私密查看 Token。

## 6. 訂單明細 `order_items`

沿用現有訂單明細欄位：

| 欄位 | 用途與規則 |
| --- | --- |
| `id` | 資料庫內部主鍵。 |
| `order_id` | 所屬訂單。 |
| `item_id` | 菜單快照中的餐點識別碼。 |
| `item_name` | 送單當下的餐點名稱快照。 |
| `unit_price` | 送單當下的單價快照，須為非負整數。 |
| `quantity` | 數量，須為正整數。 |
| `note` | 此餐點的選填自由文字備註；去除前後空白後最多 200 字，空白保存為空字串。 |
| `subtotal` | `unit_price × quantity`，由後端計算。 |

後端收到訂單時，必須使用團購的菜單快照重新查找餐點名稱、供應狀態及單價，不能信任瀏覽器傳入的名稱、價格、小計或總金額。

統籌彙整時使用 `item_id + note` 作為分組條件。相同餐點且備註相同才合併數量；備註不同必須分列，避免店家無法區分製作需求。

## 7. Token 產生與保存

### 7.1 統籌管理 Token

- 使用 `secrets.token_urlsafe(32)` 產生高強度隨機 Token。
- 原始 Token 只在建立團購成功時回傳一次，之後不寫入資料庫、日誌或錯誤訊息。
- 資料庫只保存原始 Token 的 SHA-256 雜湊值。
- 驗證時將收到的 Token 以相同方式雜湊，再使用 `hmac.compare_digest` 比對。
- 管理連結只能交給統籌，不得包含在公開團購頁、公開 QR Code 或菜單資料中。

### 7.2 個人訂單查看 Token

- 每張個人訂單使用獨立的 `secrets.token_urlsafe(32)` 產生查看 Token。
- 原始 Token 只在送單成功時回傳給該參與者。
- 資料庫只保存 SHA-256 雜湊值，驗證方式與管理 Token 相同。
- 取得某張訂單的 Token 不能查看其他人的訂單或團購彙整。

SHA-256 適用於本規格的隨機高強度 Token；若未來加入使用者密碼，密碼必須改用專用的慢速密碼雜湊方法，不能套用此規則。

## 8. 權限區分

| 持有資料 | 可以做的事 | 不可以做的事 |
| --- | --- | --- |
| 公開團購代碼 | 進入團購、查看菜單、在 `open` 狀態送單 | 查看所有人訂單、關閉團購、取得管理 Token |
| 個人訂單編號與查看 Token | 查看該筆個人訂單 | 查看其他訂單、查看彙整、關閉團購 |
| 統籌管理 Token | 查看個人明細與餐點彙整、關閉團購 | 取得原始 Token 的資料庫值（資料庫沒有保存） |
| 資料庫內部 `id` | 僅供系統建立關聯 | 不可單獨用來通過公開或管理權限驗證 |

管理 Token 或個人查看 Token 驗證失敗時，回應應使用一般化的拒絕訊息，不可把 Token、雜湊值或其他人的資料放進錯誤內容。

## 9. 建立個人訂單的驗證流程

後端必須在單一資料庫交易中完成：

1. 以公開團購代碼找到團購，確認狀態為 `open`。
2. 讀取該團購的菜單快照。
3. 驗證參與者姓名不為空，且長度不超過 50 個字元。
4. 驗證至少選擇一個餐點，所有數量皆為正整數。
5. 驗證每個餐點備註不超過 200 字；備註只能描述需求，不能修改價格。
6. 確認每個餐點存在於快照中且仍為供應狀態。
7. 使用快照內的單價重新計算明細小計與總金額。
8. 取得並遞增團購的 `next_order_sequence`。
9. 產生個人訂單編號與私密查看 Token，僅保存 Token 雜湊。
10. 寫入訂單與所有明細；任一步驟失敗時整筆取消。

## 10. 邏輯資料範例

下列範例用來說明資料關係，不代表資料庫會把所有內容存在同一欄位。範例刻意不包含任何真實或可使用的 Token。

```json
{
  "group": {
    "public_code": "ABC234",
    "status": "open",
    "next_order_sequence": 3,
    "created_at": "2026-08-07T06:30:00Z",
    "closed_at": null
  },
  "menu": {
    "restaurant": {
      "name": "示範小館"
    },
    "categories": [
      {
        "id": "main-dishes",
        "name": "主餐",
        "items": [
          {
            "id": "braised-pork-rice",
            "name": "滷肉飯",
            "description": "經典台灣風味",
            "price": 60,
            "available": true
          }
        ]
      }
    ]
  },
  "orders": [
    {
      "public_order_number": "ABC234-001",
      "customer_name": "小美",
      "total_amount": 120,
      "items": [
        {
          "item_id": "braised-pork-rice",
          "item_name": "滷肉飯",
          "unit_price": 60,
          "quantity": 2,
          "note": "小辣",
          "subtotal": 120
        }
      ]
    }
  ]
}
```

建立團購或個人訂單的回應可以分別帶回 `<management-token-returned-once>` 或 `<order-access-token-returned-once>` 這類概念欄位；文件與測試資料不得放入真實 Token。

## 11. 後續 SQLite 建議限制與索引

- `group_sessions.public_code`：`UNIQUE NOT NULL`。
- `group_sessions.status`：限制為 `open` 或 `closed`。
- `group_sessions.management_token_hash`：`UNIQUE NOT NULL`。
- `group_menus.group_session_id`：`PRIMARY KEY` 或 `UNIQUE`，並連到團購。
- `orders.public_order_number`：團購訂單必須唯一；既有訂單允許 `null`。
- `orders.group_session_id, orders.created_at`：建立複合索引，供統籌依團購讀取訂單。
- `orders.order_access_token_hash`：團購訂單必須唯一；既有訂單允許 `null`。
- 第一版不刪除團購，因此外鍵不使用連鎖刪除。

## 12. 錯誤回應原則

| 情況 | 建議 HTTP 狀態 | 安全回應方向 |
| --- | --- | --- |
| 團購代碼不存在 | 404 | 顯示找不到該團購。 |
| 團購已關閉仍送單 | 409 | 顯示團購已截止，不能新增訂單。 |
| 菜單或訂單格式錯誤 | 422 | 指出可修正的欄位，不回傳機密資料。 |
| 管理或個人查看 Token 無效 | 403 | 顯示無權查看，不說明正確 Token 或雜湊資訊。 |

伺服器日誌不得記錄管理 Token、個人查看 Token、API Key、Cookie 或其他機密資訊。

## 13. 本規格暫時不處理

- 店家固定菜單模式的資料表與店家管理權限。
- 會員登入、帳號密碼與角色系統。
- 線上付款、外送、通知、POS 或店家自動接單。
- 參與者修改或取消已送出的訂單。
- 團購重新開啟、刪除或永久封存。
- 自動傳送訂單給店家；第一版由統籌複製彙整內容後自行聯絡店家。

## 14. 需求追溯

- `FR-14`：以公開團購代碼進入同一個團購。
- `FR-15`：統籌管理資訊與公開代碼分離，且管理 Token 只保存雜湊。
- `FR-17`：每位參與者建立獨立訂單與個人訂單編號。
- `FR-20`：關閉團購後拒絕新增訂單，但保留統籌查看與彙整能力。
